# Codex 작업 프롬프트 — 온점. 네이티브 MVP 1차 개발

당신은 `온점.`(Onjeom) 프로젝트의 개발을 인수받은 시니어 모바일 앱 엔지니어이자 제품 UX 엔지니어입니다. 이 저장소에 **이미 동작하는 웹/PWA 프로토타입**이 있으므로 처음부터 새로 기획하거나 기존 구현을 덮어쓰지 말고, 검증 가능한 모바일 MVP로 확장하십시오.

## 0. 착수 및 검증
1. `AGENTS.md`, `README.md`, `CODEX_TASK.md`, `src/logic.mjs`, `src/app.mjs`, `tests/`를 읽으십시오.
2. 작업 전 `npm test`를 실행해 기준 결과를 기록하십시오. 기존 테스트를 삭제하거나 무시하지 마십시오.
3. 웹 프로토타입을 실행해 핵심 화면과 상호작용(오늘/정원/도감/씨앗 보관함)을 확인하십시오. 브라우저 검증에 필요한 도구가 없으면 그 사실을 명시하십시오.
4. 현재 구현과 미구현 범위를 분리해 짧게 보고한 후 코드 변경을 시작하십시오.

## 1. 제품 목표와 변경 불가 원칙
- 서비스명: **온점.** / 한국어 중심, iOS·Android 지원.
- 포지셔닝: **생각을 정리하고, 지금 할 수 있는 한 걸음씩 실행한 결과가 꽃으로 남는 차분한 감성 앱.** ADHD나 디지털 치매의 진단·치료 효능을 주장하지 마십시오.
- 핵심 흐름: 자유롭게 생각 입력 → 작업 단위로 분리 → 사용자가 결과 검토·수정 → 한 번에 한 가지 행동 제시 → 완료/나중에/더 작게 → 식물 성장 → 꽃 개화 → 꽃말 감상 → 자발적 도감 등록.
- 식물 성장 조건은 **실제 완료한 할 일**입니다. 집중한 시간에 연동하는 집중 타이머 앱으로 바꾸지 마십시오. 기존 기준은 `4`개 완료마다 한 번 개화이며 향후 설정으로 분리할 수 있습니다.
- 미완료 일은 씨앗 보관함에 보관하고 복원합니다. 연속 출석 보상, 식물 시들기, 시간 제한 페널티, 과도한 알림을 기본 기능으로 만들지 마십시오.
- 희귀색/시즌꽃: 기존 기본 꽃 12종과 희귀 변이 및 크리스마스·할로윈·새해 꽃 데이터 유지. 추석은 음력 이동 명절이므로 신뢰할 수 있는 연도별 데이터 없이 날짜를 추정하거나 고정하지 마십시오. 확률은 **개발용 제안값**이며 결제 여부와 무관해야 합니다.
- 꽃말은 전통 꽃말로 가장하지 않고 **온점.의 창작 문구**로 명시합니다. 꽃말 열람과 카드 저장은 광고 없이 무료로 유지합니다.
- 도감 최초 등록: **무료 사용자가 새로운 품종+색상 조합을 처음 등록하기로 선택했을 때만** 보상형 광고 시청 기회를 제공합니다. 중복 등록은 광고 없음. PLUS 사용자는 광고 없이 등록. 광고를 보지 않거나 로딩 실패·취소·보상 검증 실패해도 꽃은 영구적으로 미등록 보관되고 나중에 재시도할 수 있습니다. 강제 광고/현금 가챠/유료 희귀 확률 상승은 금지합니다.
- 기존 `premiumDemo`와 광고 시뮬레이션은 **실제 결제나 실제 광고가 아님**을 모든 화면과 README에서 명확히 표시하십시오.

## 2. 이번 구현 범위 (우선순위 순)
### P0. 네이티브 모바일 앱
- 공식 Expo 문서를 확인한 뒤 해당 환경에서 설치 가능한 안정 SDK와 React Native/Expo Router를 선택합니다. 버전은 확인하지 않고 지어내지 마십시오.
- 기존 `src/logic.mjs` 순수 도메인 함수를 최대한 공유하고, 기존 웹 프로토타입은 보존하십시오. 새 앱은 `apps/mobile/` 폴더에 만들어도 됩니다.
- 한국어 화면: **오늘**, **생각 비우기**, **한 걸음**, **정원**, **꽃 도감**, **미완료 씨앗**. 탭 3~4개와 필요한 모달/시트로 단순화하십시오.
- 감성 방향: 크림·세이지·소프트 샌드, 깨끗한 한국어 타이포그래피, 여백, 작은 식물 모션, 시각적 대비·접근성 확보. 애니메이션은 최소화 옵션 제공. 튜토리얼과 기능 설정은 적게.
- 할 일: 추가, 분리된 할 일 검토·제목 수정·삭제·순서 변경, 단일 작업 화면, 완료, 나중에, 이어하기, 작은 단계로 나누기. **사용자가 입력하지 않은 마감·우선순위·시간을 사실처럼 자동 추가하지 않기.**
- 꽃 성장·개화 및 도감: 12종, 기본 색+희귀 변이, 시즌 꽃, 꽃말 상세, 개화 날짜, 원래 완료한 행동 연계, 중복 도감 등록 광고 생략, 아직 미등록인 꽃 목록.
- 데이터: SQLite 등 기기 내 영속 저장, 스키마 버전·마이그레이션, 손상 복구, 데이터 삭제, 가능한 경우 JSON 내보내기. 회원가입 없이 바로 시작.

### P1. 광고·AI·결제 경계
- 광고는 이번 단계에서 **명확한 개발용 모의 인터페이스**로 유지하고, 실제 시청이 없는데 실제 광고를 시청했다고 주장하거나 숨겨서 성공 처리하지 마십시오. 실제 Google AdMob SDK, 앱스토어 결제, 구독 서버 검증은 계정 및 상품 설정이 제공된 후에만 연동하십시오.
- 자연어 분리는 현재 로컬 규칙 기반입니다. AI라고 표시하지 말고, 나중에 서버 측 모델 호출을 교체할 수 있게 `TaskExtractor` 인터페이스를 분리하십시오. 실제 AI 호출은 명시적 동의·서버 API·비용 제한·개인정보 설계 전까지 보류하십시오.
- 과도한 사용량 분석, 광고 타깃팅을 위해 사용자의 작업 원문을 전송하는 기능은 넣지 마십시오.

### P2. 제품 완성도
- 오류 상태, 빈 화면, 기기 접근성 설정, 저장 실패, 앱 중단/복귀, 작은 화면, 다크모드 우선순위 판단, 최소한의 오프라인 경험을 구현하십시오.
- 정원은 현재 진행 중인 작은 화분과 지금까지 피운 꽃의 **기억의 정원**을 구분합니다.
- 기본 계절 배경 변화와 꽃말 카드 미리보기 기능을 넣되, 앱 핵심 실행 흐름을 가리지 않도록 배치합니다.

## 3. 자동 테스트 및 검수 기준
- 기존 `npm test` 전부 통과.
- 추가 테스트: 생각 분리·수정, 작업 순서, 4회 완료 시 개화, 도중 앱 종료 후 이어하기, 미완료 보관/복원, 고정일 시즌 경계, 희귀 변이 결정성(주입 난수), 최초 품종+색상 등록, 중복 등록 광고 면제, PLUS 데모 우회, 광고 취소/재고 부족 시 미등록 꽃 보존, 데이터 마이그레이션.
- iOS/Android 실제 기기나 시뮬레이터에서 검증했다면 대상 버전과 실행 결과를 명시하십시오. 실행하지 못한 경우 **실행했다고 주장하지 마십시오**.
- 실행 명령, 필요한 환경변수, 플랫폼별 실행 방법, 테스트 결과, 변경 파일, 남은 과제를 README에 문서화하십시오.

## 4. 결과물과 종료 조건
1. `apps/mobile` 또는 합리적인 구조의 **실제 실행 가능한 네이티브 앱 소스**.
2. 기존 웹 프로토타입과 테스트 보존.
3. 유지 가능한 도메인 로직·데이터 스키마, 명료한 한국어 UI.
4. 추가한 테스트가 실행되고 모두 통과(실패 시 원인·해결 기록).
5. 실제 연결되지 않은 광고/결제/AI는 어떤 화면에서도 실서비스로 오인되지 않게 표시.
6. 변경 내역을 커밋하고, 가능하면 별도 개발 브랜치 및 PR을 작성하십시오. 새 저장소 여부는 사용자 지시에 따르고 다른 게임인 `haruhandang` 프로젝트를 수정하지 마십시오.

필수 원칙: **꽃을 키우기 위해 일을 하는 앱이 아니라, 복잡한 하루를 한 걸음씩 정리하다 보니 어느새 꽃이 피는 앱.**
